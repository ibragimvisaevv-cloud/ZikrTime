# Дополнительные сведения о местах и исправления

Статус: код и проверки на искусственных данных подготовлены. Рабочий бот, база,
хранилище и Telegram в рамках этой работы не менялись; развёртывание **не выполнено**.
Проверки приложения не доказывают доступность живой модерации или загрузку тайлов карты.

## Совместимость данных

`places.json` остаётся `version: 1`. Старые обязательные поля и ID сохраняются.
Новые поля записи необязательны: `women` (Boolean/null), `access_conditions`, `entrance`,
`source_details`, `confirmed_at` (строка YYYY-MM-DD). `wudu` также Boolean/null.
`false` означает «нет», `null`/отсутствие — «нет данных». Строки `"false"`, `"true"`,
числа и объекты не трактуются как Boolean. Пустые текстовые поля не публикуются.

При отсутствии `women` Android понимает старые явные `who=both/women/men`;
явное `women:null` отменяет этот вывод и показывает «нет данных». Старые клиенты
продолжают читать `who` и игнорируют новые поля. Старые метки не переопределяются
неявно при исправлении другого поля. Это совместимость формата, а не одинаковый UI
старой версии и новой.

`src=osm` сохраняет происхождение записи даже после правки. `source_details` описывает
источник уточнения. Ни время OSM-импорта, ни `created`, ни технический `updated`, ни
дата одобрения не подставляются вместо `confirmed_at`. Дату фактической проверки
пользователь предлагает явно; модератор проверяет её. Автоматического утверждения
«сейчас открыто» нет.

На верхнем уровне новый сервер публикует `corrections_enabled: true`. Старые клиенты
игнорируют флаг. Новый Android включает переход к исправлениям только при явном
Boolean `true` из списка мест; отсутствующее/некорректное значение выключает переход.
Поэтому до развёртывания кнопка сообщает, что ссылка пока недоступна.

## Цепочка и ограничения

1. Android открывает `tg://resolve?domain=<bot>&start=fix_<placeId>`, при отсутствии
   приложения — HTTPS `https://t.me/<bot>?start=fix_<placeId>`. ID не теряется.
2. Бот проверяет наличие опубликованного места, предлагает поле и значение.
   Открытие бота, выбор поля и предпросмотр **не отправляют заявку**.
3. Только явная кнопка отправки создаёт `place_corrections[requestId]` со статусом
   `pending` в существующей закрытой базе. Публичный список не меняется.
4. В меню администратора есть «Исправления мест». Администратор видит место/ID,
   поле, прежнее и предложенное значение, затем одобряет или отклоняет.
5. Одобрение проверяет, что запись всё ещё опубликована и поле не изменилось со
   времени заявки. Конфликтующую заявку нельзя тихо применить поверх новой правки.
   Отказ не меняет карточку. Повторная отправка/решение не создают дубль.
6. При одобрении обновляются только выбранное поле и технические метки; `edited=true`
   защищает ручную правку от следующего OSM-импорта. Публикация использует существующий
   `Bot.save()` и `write_places()`. Пользователь и администратор получают уведомления
   после стандартного сохранения через BufferedTelegram.

Общая архитектура сохраняет закрытый JSON условной записью с ETag, а затем отдельно
публикует публичный JSON. Это не единая транзакция между объектами хранилища. При сбое
публикации следует повторить публикацию из уже сохранённой базы; нельзя откатывать
всю базу поверх появившихся заявок. В тестах живая инфраструктура не используется.

## Проверки перед развёртыванием

В корне репозитория:

```sh
python3 -B shop-bot/test_bot.py
python3 -B shop-bot/test_miniapi.py
python3 -B shop-bot/test_place_corrections.py
node --check shop-bot/miniapp/app.js
./gradlew :app:testDebugUnitTest --tests com.zikrtime.app.data.PlacesTest
```

Целевые Python-тесты покрывают восемь сценариев: открытие/отмену без отправки,
отправку→очередь→одобрение→публикацию, отказ/неизвестное значение, права доступа и
повторы, конфликт старой заявки, реальные даты и сохранение правки при OSM-импорте,
неверные типы/поля и скрытые места. Сеть в этих тестах принудительно запрещена.
JVM-проверки покрывают пустые/битые данные, Boolean/null, старый `who`, даты,
дубликаты ID, точную ссылку и флаг доступности исправлений.

## Порядок согласованного rollout

Эти действия выполняются только после отдельного разрешения владельца на живой
backend. Текущая ветка и Android-сборка сами по себе не являются таким разрешением.

1. Зафиксировать проверенный SHA и резервную версию закрытой базы средствами
   хранилища. Использовать существующие секреты среды развёртывания; не переносить
   их в Git, документацию, сообщения или логи.
2. Развернуть из этого SHA webhook Vercel с `index.py` и `place_corrections.py` вместе.
   Миграция минимальна: `setdefault("place_corrections", {})` при чтении базы;
   старые записи и чужие данные не переписываются.
3. Обновить Yandex Cloud Function Mini API из того же SHA. `deploy_api.py` уже
   включает `place_corrections.py` в ZIP, поскольку Mini API импортирует `index.py`.
   Нельзя выкладывать только новый `index.py` без helper-модуля.
4. В отдельной тестовой базе/бакете и тестовом боте пройти полный сценарий с
   искусственным местом: две несовместимые заявки, отказ, одобрение, повтор кнопки,
   обычный пользователь вместо администратора. Проверить сохранённый JSON и отсутствие
   автора/очереди в публичном файле. Производственные заявки для теста не создавать.
5. В рабочей среде после проверки версии выполнить однократную публикацию текущего
   `places.json` существующим `Bot.write_places()`/`Bot.save()` с `places_dirty=True`.
   Новые сведения не выдумывать и OSM-импорт ради включения функции не запускать.
   Публичный файл теперь содержит `corrections_enabled:true`.
6. Прочитать публичный JSON и проверить флаг, прежние ID, отсутствие личной очереди.
   В Android обновить раздел мест, проверить доступность передачи конкретного ID,
   отмену до отправки, HTTPS fallback. Открытие бота не считать отправленной заявкой.
   Отдельно проверить офлайн сохранённый список, отказ GPS и карту с реальными тайлами.

Обычный workflow `Shop bot` выполняет также инфраструктурные действия и OSM-импорт;
его не следует запускать целиком только ради этой функции без согласования этих
действий. CI новой Android-ветки запускает лишь тесты, не deployment.

## Rollback

1. При необходимости сначала выключить исправления в актуальном публичном JSON
   (`corrections_enabled:false`), сохранив остальные актуальные данные.
2. Вернуть предыдущую версию webhook и Mini API согласованно. Старый код игнорирует
   `place_corrections` и дополнительные поля; не удалять накопленные заявки и не
   восстанавливать старую базу поверх новых пользовательских изменений.
3. Повторно опубликовать текущие одобренные места с выключенным/отсутствующим флагом.
   Учесть CDN/cache до 60 секунд и локальную сохранённую копию клиента.
4. После устранения ошибки развернуть совместимые версии, проверить очередь и
   повторить публикацию. Заявки с `approved/rejected` не переводить в `pending`
   автоматически; конфликтующие заявки рассматривает администратор.
